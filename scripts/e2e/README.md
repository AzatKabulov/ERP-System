# Real-stack browser run

One browser session that drives the **real** Flutter web build against the **real** Django API and PostgreSQL. It is not part of CI (it needs a browser, a database and both servers). It was run for Phases 1-9; the result is recorded in `HANDOFF.md`.

What it covers (see HANDOFF for the count): sign-in as owner, exchange rate, products priced in TMT and USD, supplier, purchase order (draft, submit), a partial receipt, a receipt whose **answer is dropped after the server committed**, a page reload standing in for a tablet restart (exactly one delivery, no duplicate, nothing left pending), stock value (FIFO), history. **Sales (Phase 5):** a sale from the Warehouse at a price the seller types (100 instead of the catalog 120), paid in cash (total, price, payment method, FIFO cost and stock checked in the database), the Receipt button downloading a PDF, a second sale paid by card whose answer is dropped after commit followed by a reload (exactly two sales, numbers 1 and 2, stock exactly 5), the history, and the receipt fetched from the API in Russian and in Turkmen and read back with `pypdf` (`pdf_text.py`; the price charged, how it was paid, no cost, change, discount or invoice wording). **Transfers and counts (Phase 6):** the owner sends 2 pieces from the Warehouse to the shop (they wait in transit, the warehouse drops to 3), the shop receives only 1 with a reason while **the answer is dropped after commit**, then a reload (still one transfer, 1 piece at the shop, nothing pending, ledger consistent), and a stock count at the warehouse (3 in the system, 2 found, sent, explained and approved; the warehouse holds 2). **Returns and reordering (Phase 7, `phase78.js`):** a customer brings back 1 of the 3 pieces of S-000001 (refund 100,00, the price charged, back on the shelf), then the other 2 as damaged (refund 200,00, so the two refunds add up to the sale and the Return button disappears); a return on S-000002 (card) whose **answer is dropped after commit**, then a reload (exactly three returns, stock exactly 4); a damaged piece goes back to the supplier (credit 50,00 from the delivery price); a minimum and target for the shop gives a reorder suggestion of 19 and a draft purchase order PO-0002. **Expenses, warranty and CSV (Phase 8):** an expense with a receipt photo chosen through the browser's file dialog (Playwright answers the `filechooser` event), the private file served to a signed-in member byte for byte and refused without a sign-in, the receipt fetched through the app, the expense voided (not deleted) and out of the total; a warranty claim from S-000002 closed with a replacement (one sellable piece out, one damaged piece in); a CSV import whose file has an existing SKU and an unknown unit (the page names both, **nothing is created, not even the valid row**), then a fixed file (three products, one with Turkmen letters, no stock created) and the catalog export downloaded (`products.csv`, BOM, `;`). **Dashboard, reports and activity (Phase 9, `phase9.js`):** a second expense is added and then the owner's dashboard and every report tab are read back against figures worked out from the database itself (revenue, refunds, net sales, cost of goods, gross profit, expenses, result, stock value), the place filter, the sales CSV, and the activity history (search and the action menu). Then Russian to Turkmen and back after a reload, sign-out, and the warehouse user seeing no costs, no credit on supplier returns, no Reports page and a dashboard without money; a manager (the same reports) and a seller (sales only, no costs) are checked too. It also checks the ledger, purchasing, sales, transfer and warranty `reconcile` consistency through the database.

## Run it

1. Start PostgreSQL and write `backend/.env` (`bash scripts/claude_cloud_postgres.sh` on the Claude cloud VM), then `cd backend && uv run python manage.py migrate && uv run python manage.py createcachetable`.
2. `bash scripts/e2e/reset_db.sh` (**flushes the database**; local throwaway only).
3. Build the web app for the local API: `cd mobile && flutter build web --no-web-resources-cdn --dart-define=API_BASE_URL=http://127.0.0.1:8000`.
4. Start the API with CORS for the web origin: `cd backend && DJANGO_CORS_ALLOWED_ORIGINS=http://127.0.0.1:8080 uv run python manage.py runserver 127.0.0.1:8000 --noreload`.
5. Serve the build: `cd mobile/build/web && python3 -m http.server 8080 --bind 127.0.0.1`.
6. `node scripts/e2e/real_stack.js` (needs `uv` and the backend dev dependencies on the PATH for the database checks and the PDF text). Environment: `PLAYWRIGHT_MODULE` (path to the playwright package), `CHROMIUM_PATH`, `E2E_WEB_URL`, `E2E_OUT` (screenshots).

The Russian labels in the script follow `mobile/lib/l10n/app_ru.arb`; if a label changes, update the script.

`phase78.js` and `phase9.js` hold the Phase 7-8 and Phase 9 sections. To work on one without waiting for the earlier phases: run the script once with `E2E_STOP_AFTER=phase6` (or `phase78`; it stops there), take a database snapshot with `pg_dump`, and then restore the snapshot and run `E2E_RESUME=phase78` (or `phase9`) `node scripts/e2e/real_stack.js` (it signs in as the owner and continues from there). A full run still starts from `reset_db.sh`.

`clickLabel` scrolls a control into view first when it is below or above the visible part of a long page (the product form is taller than the browser window), as `fill` always did.

A harness quirk worth knowing: an idle Flutter web page draws no frame, so right after a dialog closes the accessibility tree (which the script clicks and types through) can still describe the page as it was before, with the new line's field where the next button now is. The script moves the mouse after closing the product picker so a frame is drawn and the tree refreshes before the next click.
